El viaje de una petición HTTP

Cada vez que un navegador pide una página, esa petición hace un recorrido con paradas fijas: como un tren que sale de una estación, cruza varias líneas y llega a destino. Este sitio reimagina el protocolo HTTP como un mapa de ruta, donde cada método, cada código de estado y cada versión del protocolo es una línea con su propio color.

Línea A · Conceptos básicos

Arquitectura cliente-servidor

HTTP se apoya en un paradigma estricto: el cliente abre la conexión y envía una petición; el servidor escucha, procesa y responde. Es un ciclo atómico e independiente que se repite en cada intercambio, como cada viaje de un tren entre dos estaciones.

HTTP es stateless (sin estado): el servidor no recuerda peticiones anteriores. Esto simplifica el diseño y facilita escalar, pero obliga a usar cookies o tokens —el "boleto" que el cliente muestra en cada viaje— para mantener la sesión.

Línea B · Verbos HTTP

Métodos como paradas de la línea

Cada verbo es una parada con una función fija. Usar la parada correcta habilita ventajas automáticas, como el caché de los GET.

GETparada de lectura

Solicita la representación de un recurso. Segura e idempotente: repetirla no cambia el estado del servidor.

POSTparada de creación

Envía datos para crear un nuevo recurso o procesar una carga útil. No es idempotente.

PUTparada de reemplazo

Reemplaza por completo el recurso objetivo. Idempotente: repetirla da el mismo resultado.

Ejemplo práctico con JavaScript

La Fetch API del navegador emite peticiones HTTP reales desde JavaScript. Estos ejemplos muestran un boleto de ida GET y uno de creación POST:

fetch-get.js
fetch("https://api.ejemplo.com/usuarios/12")
  .then(function (response) { return response.json(); })
  .then(function (data) { console.log(data); })
  .catch(function (error) { console.error("Error:", error); });
fetch-post.js
fetch("https://api.ejemplo.com/usuarios", {
  method: "POST",
  headers: { "Content-Type": "application/json" },
  body: JSON.stringify({ nombre: "Ana", correo: "ana@ejemplo.com" })
})
  .then(function (response) { return response.json(); })
  .then(function (data) { console.log("Creado:", data); });

Línea C · Anatomía de la respuesta

Tablero de salidas: códigos de estado

Como en un tablero de aeropuerto, cada código de tres dígitos anuncia de inmediato el resultado del viaje. El primer dígito indica la familia.

1xxInformativosLa petición fue recibida y el proceso continúa. Ej. 100 Continue.
2xxÉxito200 OK es el estándar de éxito; 201 Created confirma que un POST generó un nuevo registro.
3xxRedirecciónEl cliente debe tomar una acción adicional. Ej. 301 Moved Permanently.
4xxError del cliente404 Not Found, 400 Bad Request y 401 Unauthorized son los más comunes.
5xxError del servidor500 Internal Server Error: el servidor falló al procesar una solicitud aparentemente válida.

Aporte personal: los códigos de estado son la verdadera interfaz de usuario de una API. Devolver siempre 200 OK con un error encapsulado en el JSON es un antipatrón: usar el código correcto facilita la depuración y hace el software más predecible.

Línea D · Historia y seguridad

Tres vías hacia HTTP/3, y la terminal HTTPS

Piensa en HTTP/1.1, HTTP/2 y HTTP/3 como tres vías que salieron en distintas épocas pero llegan a la misma terminal: una comunicación más rápida y segura entre cliente y servidor.

1997

HTTP/1.1

Introdujo las conexiones persistentes (keep-alive), permitiendo enviar varias peticiones por la misma conexión TCP.

2015

HTTP/2

Protocolo binario con multiplexación: varias peticiones y respuestas viajan a la vez sobre una sola conexión TCP, eliminando el bloqueo de cabeza de línea.

2022

HTTP/3

Abandona TCP por QUIC, basado en UDP. Reduce la latencia de conexión y mejora la estabilidad en redes móviles.

Terminal HTTPS: HTTP sobre TLS

HTTPS no es una vía distinta, sino HTTP circulando sobre una capa de cifrado SSL/TLS. Toda ruta segura pasa por tres andenes:

Cifrado

Los datos viajan ininteligibles para terceros.

Integridad

Los datos no pueden alterarse en el camino.

Autenticación

Confirma que el servidor es quien dice ser.

Cuando los cimientos como TCP se vuelven un cuello de botella, a veces la única forma de avanzar es tender una vía nueva —esa es la lección de HTTP/3. Hoy, HTTPS dejó de ser un lujo de pasarelas de pago para convertirse en el estándar mínimo de cualquier transmisión de datos.

Glosario de la ruta

Términos que aparecen en el recorrido, explicados en una línea. Haz clic en cada uno para expandirlo.

Stateless (sin estado)
El servidor no guarda memoria de peticiones anteriores del mismo cliente; cada viaje es independiente del anterior.
Idempotente
Una operación es idempotente si repetirla varias veces produce el mismo resultado que hacerla una sola vez (como GET o PUT).
Multiplexación
Capacidad de HTTP/2 de enviar varias peticiones y respuestas al mismo tiempo por una sola conexión, sin esperar a que termine la anterior.
Handshake TCP
El intercambio inicial de mensajes entre cliente y servidor para establecer una conexión confiable antes de transmitir datos.
TLS / SSL
La capa de cifrado que convierte HTTP en HTTPS, garantizando cifrado, integridad y autenticación del servidor.
Cache-Control
Cabecera que le dice al navegador cuánto tiempo puede reutilizar una respuesta sin volver a pedirla al servidor.
